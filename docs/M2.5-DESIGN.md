## 2. Design decisions

**R1 — Two files, one authoritative, source-aware.** `config.json` holds the V1 document and is
authoritative. `launcher.json` holds the legacy array and is frozen: read-only, never written,
never deleted, consulted **only** when `config.json` is absent. Each file has a required shape,
and a well-formed document in the wrong file is a distinct reported state — never reinterpreted,
never adopted, never overwritten.

**R2 — The codec is untouched; source-awareness lives in the store.** `ConfigurationDecoder.decode`
returns `.legacy` for any JSON array regardless of origin, and that must not change. The new
`ConfigurationStore` applies a per-source interpretation on top of the unchanged codec state:
`.legacy` from `config.json` is `wrongFormat`, and `.v1`/`.unsupportedVersion` from
`launcher.json` is `wrongFormat`. `Configuration.swift` gains no lines.

**R3 — Readers never lock; writers always do.** `rename(2)` gives atomic visibility, so a reader
always sees one complete document. Pure reads take no lock. Anything that writes — including
migration-on-read — holds one exclusive advisory lock and re-reads state inside it.

**R4 — Migration runs on read, never memoized.** ADR-007's "runs on read" is preserved literally.
The store keeps no in-memory document cache, matching ARCHITECTURE §1's stateless request
handling and today's `Launcher.selected()`, which also re-reads per request.

**R5 — No write may block the shared HTTP queue.** The lock is `LOCK_NB` and never waited on.
Contention yields `503` for a write and a read-only response for a migration-on-read (F7).

**R6 — Lost updates are refused by an opaque revision token.** *(Replaces revision 2's
byte-comparison rule, which is withdrawn.)* `GET /launcher` publishes a `revision`;
`POST /launcher` must echo it as `expected`; the server recomputes it under the lock. See §6.

**R7 — Three-phase commit with one safely replaced generation.** Pre-commit validation → atomic
replacement → post-commit verification. The previous generation is retained as `config.json.prev`,
prepared under a temporary name and swapped in by `rename`, so an existing backup is never
unlinked before its successor exists. See §7.

**R8 — Durability is `fsync`, best-effort where it cannot be undone.** `fsync(fd)` on the temp
file before the rename, and it is **fatal** because nothing is visible yet. `fsync(dirfd)` after
the rename is **best-effort** because macOS guarantees no directory-`fsync` semantics and
`F_FULLFSYNC` on a directory fd returns `EINVAL`. `F_FULLFSYNC` is used nowhere. The behaviour is
measured on the target build, not assumed. See §11.3.

**R9 — The product cap becomes a writer rule at 7.** `maximumAppControls = 7`, enforced on the
write path and on the writable-state rule. `ConfigurationDecoder.maximumControlCount` stays 4096
as a corruption guard, as ADR-015 intended. The client's `APP_SLOTS = 7`
(`web/index.html:262`) remains an independent UX constant; unifying them is M3 work (U6).

**R10 — Preservation replaces filtering.** The write path performs **no** `Apps.isKnown` check. An
uninstalled app's path, an empty path and a duplicated path are all stored. Preservation is not
authorization: `ActionRegistry.dispatch` re-validates and re-authorizes against `Apps.isKnown` on
every launch (`ActionRegistry.swift:118-127`), and `.unmodeled` parameters have no conversion to
`ActionParameters` at all (ADR-015 rule 3). What the writer rejects is bounded and reported: more
than 7 entries, or an entry over 4096 bytes.

**R11 — A save is refused when the page could not have shown the whole deck.** If
`legacySelection(v1) == nil`, or the document holds more than 7 controls, then `paths=` cannot
express it and a save would destroy what the editor cannot render. `POST` returns `409`; `GET`
still returns 200 with the full selection where one exists, never a partial projection.

**R12 — Bounded, non-following reads.** The store opens with `O_RDONLY|O_NOFOLLOW`, `fstat`s the
fd, requires `S_ISREG`, and reads at most `maximumDocumentBytes + 1` bytes. A huge file is
rejected without being allocated; a symlink or FIFO fails closed instead of being followed or
blocked on. Stronger than the `Data(contentsOf:)` used by `Launcher.selected()` and `loadToken()`.

**R13 — One response shape for both methods.** `POST /launcher` returns exactly the
`GET /launcher` shape plus `saved`, so the client replaces its state wholesale and the application
catalog it renders from cannot be dropped by a save. `revision` is included, so a second edit
needs no intervening GET. See §5.1.

**R14 — `--config-dir` is a product option, not a test hook.** It redirects exactly three sites:
`main.swift:31` (config dir → token), `TLS.swift:10` (`LocalTLS.dir`) and `Control.swift:66`
(`Launcher.file`). It does **not** redirect `Control.swift:22`
(`NSHomeDirectory() + "/Applications"`), which is app-catalog state, not configuration. Absent the
option, every path is unchanged. It is the only way to make storage acceptance-testable here,
because `NSHomeDirectory()` ignores `$HOME`.

## 3. Migration state machine

Store-level types, in the new `ConfigurationStore.swift` — **not** in `Configuration.swift`:

```
enum ConfigurationStoreState {
    case ready(DeckConfigurationV1)              // config.json = V1, projectable, <= 7 controls
    case unprojectable(DeckConfigurationV1)      // legacySelection == nil
    case overLimit(DeckConfigurationV1)          // controls.count > 7
    case unconfigured                            // both files absent
    case migrationPending(DeckConfigurationV1, [String])   // derived, not yet committed
    case legacyUnrepresentable([String], ConfigurationError)
    case damaged(Source, DamageReason)           // malformed | unsupported(Int) | unreadable | notRegularFile
    case wrongFormat(Source)                     // array in config.json, or object in launcher.json
    case corrupt                                 // a failed commit could not be recovered
    case busy                                    // lock held by another process, this response only
}
enum Source { case config, legacy }
```

### 3.1 Classification (no lock, no write)

| `config.json` | `launcher.json` | State | `selected` | `writable` | `configuration` |
|---|---|---|---|---|---|
| `.v1(c)`, projectable, ≤7 controls | not consulted | `ready(c)` | paths | true | `v1` |
| `.v1(c)`, projectable, **>7 controls** | not consulted | `overLimit(c)` | **all N paths** | **false** | `too-many-controls` |
| `.v1(c)`, `legacySelection(c) == nil` | not consulted | `unprojectable(c)` | `null` | false | `unrepresentable` |
| `.legacy(_)` — an array | not consulted | `wrongFormat(.config)` | `null` | false | `wrong-format` |
| `.malformed(e)` | not consulted | `damaged(.config, .malformed(e))` | `null` | false | `malformed` |
| `.unsupportedVersion(n)` | not consulted | `damaged(.config, .unsupported(n))` | `null` | false | `unsupported-version`, `version: n` |
| `.unreadable` / symlink / non-regular | not consulted | `damaged(.config, …)` | `null` | false | `unreadable` |
| `.absent` | `.legacy(p)`, `migrateToV1(p) == .success(c)` | `migrationPending(c, p)` | `p` | true | `migrated` on the committing read |
| `.absent` | `.legacy(p)`, `migrateToV1(p) == .failure(e)` | `legacyUnrepresentable(p, e)` | **`p`** | **false** | `legacy-readonly` |
| `.absent` | `.absent` | `unconfigured` | `null` | true | `unconfigured` |
| `.absent` | `.v1(_)` / `.unsupportedVersion` | `wrongFormat(.legacy)` | `null` | false | `wrong-format` |
| `.absent` | `.malformed` / `.unreadable` / non-regular | `damaged(.legacy, …)` | `null` | false | `malformed` / `unreadable` |

Three rows carry the weight.

**`legacyUnrepresentable` serves its selection rather than hiding it.** A valid legacy file that
cannot be migrated — more than 4096 entries, an entry over 4096 bytes, or a canonical form over
1 MiB — is still rendered. It is read-only because writing a 7-control document over it would
destroy preserved data, and because a legacy write path would be a second writer, which the
approved "no permanent dual-write" decision excludes. Serving costs nothing in authority: `/icon`
and `POST /launch` both gate on `Apps.isKnown` (`Control.swift:41`, `ActionRegistry.swift:124`).

**`overLimit` serves all N paths.** `selected: null` means *cannot be expressed as a path list at
all*; a document of 8 pure `app.launch` controls is expressible, so every path goes on the wire and
the client truncates for **display** only (`web/index.html:425`, `apps.length < APP_SLOTS`),
exactly as it does today. The server never truncates on disk.

**The `wrongFormat` rows are never adopted**, even where adoption would be lossless. Adopting a
legacy array found in `config.json` would create two sources of legacy truth with undefined
precedence when both files hold arrays. The repair is one documented `mv`, and the state says so.

### 3.2 Migration transition (only from `migrationPending`)

```
GET /launcher classifies -> migrationPending(c, paths)
  flock(config.lock, LOCK_EX | LOCK_NB)
    fail -> serve paths, writable=false, configuration="migrating", no revision; write nothing
    ok   -> re-read config.json INSIDE the lock
            .v1(other)  -> another process won: adopt it, discard c, serve ready(other)
            .absent     -> commit(c):
                             tmp = mkstemp; fchmod 0600; write verifiedData(c); fsync(tmp); close
                             rename(tmp, config.json)      [no .prev: no previous generation exists]
                             fsync(dirfd)                  best-effort
                             post-verify: re-open, decode, require .v1(c') && c' == c
                               pass -> serve c, configuration="migrated", revision=fingerprint(c)
                               fail -> 500-equivalent internal state; config.json retained as
                                       evidence, never deleted; state = corrupt;
                                       configuration is NEVER "migrated"
            anything else -> another process created a broken file: adopt that state, write nothing
    unlock (defer)
```

The in-lock re-read is what prevents the race: two processes that both classify
`migrationPending` cannot both write, and a migration can never overwrite a concurrent save,
because it commits only while `config.json` is **still absent under the lock**.

## 4. Corrected wire contract

### 4.1 One response shape for both methods

Revision 2a's `launcher = d` was wrong: the POST response carried `selected`, `configuration` and
`writable` but not `all`, and `renderKeys()` resolves every path through `byPath()`, which scans
`launcher.all` (`web/index.html:405,425`). Replacing the object would have emptied the deck on
every save.

**`POST /launcher` returns exactly the `GET /launcher` shape, plus `saved`.** One shape, one
serializer, no client-side merge and no partial-object hazard. A field added to GET in future
cannot silently be missing from POST.

```json
{ "selected": ["/Applications/Safari.app", "/Applications/Xcode.app"],
  "all":      [{"name":"Safari","path":"/Applications/Safari.app"}, …],
  "configuration": "v1",
  "version": 1,
  "writable": true,
  "revision": "9f3a1c02b7d40e18",
  "saved": 2 }
```

- `selected` is `null` only when the deck cannot be expressed as a path list at all; it is never a
  subset. An over-limit document serves all N paths.
- `all` is always present and non-empty on a 200.
- `version` appears only for `unsupported-version`, where the integer *is* the diagnosis
  (ADR-015's single permitted error payload).
- `revision` appears on every 200 **except** `configuration: "migrating"`, where the store
  deliberately did not classify under coordination and must not publish a token it cannot honour.
- `saved` appears on POST only.

**Cost is net zero.** Populating `all` requires `Apps.list()`, and today's `Launcher.save` already
calls `Apps.list()` to build its `known` filter (`Control.swift:82`). R10 removes that call; R13
restores it for the response. The save path performs the same single catalog scan it performs
today — it just no longer uses the result to delete entries.

### 4.2 Request contract

```
POST /launcher?k=<token>
Content-Type: application/x-www-form-urlencoded

n=<decimal>&paths=<percent-encoded, "\n"-separated>&expected=<revision>
```

`paths` alone cannot distinguish an empty selection from a selection holding one empty path:
`[].join('\n')` and `[""].join('\n')` are both `""`. No choice of separator or
`omittingEmptySubsequences` value fixes a zero-versus-one ambiguity, so `n` supplies the count and
makes a disagreement **loud** rather than silent.

The parse is a total function with exactly one branch:

```
parseSelection(params) -> Result<[String], Token>
  paths = params["paths"] ?? ""
  guard let nText = params["n"] else {
      // pre-M2.5 client: reproduce main.swift:147 exactly
      return .success(paths.split(separator: "\n"))                  // omittingEmptySubsequences: true
  }
  guard nText is a canonical unsigned decimal (no sign, no leading zero, no whitespace, non-empty),
        0 <= n <= 7 else { return .failure(.invalidCount) }
  if n == 0 {
      guard paths.isEmpty else { return .failure(.countMismatch) }   // the ONE ambiguous case
      return .success([])
  }
  let elements = paths.split(separator: "\n", omittingEmptySubsequences: false)
  guard elements.count == n else { return .failure(.countMismatch) }
  guard elements.allSatisfy({ $0.utf8.count <= 4096 }) else { return .failure(.entryTooLong) }
  return .success(elements.map(String.init))
```

The invariant that makes this correct: for a non-empty string, splitting without omitting empty
subsequences yields exactly `newlineCount + 1` elements, so `n` and `paths` agree by construction
for every `n >= 1` — including `n = 1` with an empty `paths`, which **is** the one-empty-path case
and must be accepted. Only `n == 0` needs a special rule, because an empty `paths` splits to one
element rather than zero. An `n` parameter that is present but empty selects no branch: it is
`invalid-count`, not the legacy path. Only a completely absent `n` means "old client".

| `n` | `paths` | Selection | Result |
|---|---|---|---|
| absent | `""` | `[]` | legacy branch, 0 controls |
| absent | `"a\n\nb"` | `["a","b"]` | legacy branch, empty dropped — unchanged from today |
| `0` | absent or `""` | `[]` | 0 controls |
| `0` | `"/A.app"` | — | `400 count-mismatch` |
| `1` | `""` | `[""]` | **1 control, `.appPath("")`** |
| `2` | `"\n"` | `["",""]` | 2 empty controls |
| `2` | `"/A.app\n"` | `["/A.app",""]` | trailing empty preserved |
| `2` | `"\n/A.app"` | `["","/A.app"]` | leading empty preserved |
| `2` | `"/A.app\n/A.app"` | duplicates | both preserved, ids `app-1`/`app-2` |
| `1` | `"/A.app\n/B.app"` | — | `400 count-mismatch` |
| `2` | `"/A.app"` | — | `400 count-mismatch` |
| `8` | any | — | `400 invalid-count` |

`n`/`paths`/`expected` syntax checks live in `DeckRoute.validateParameters`, which is pure and
already runs before side effects for `/launch` and `/claude` (`HTTPParsing.swift:265-278`,
ARCHITECTURE §5 step 6). The shared handler re-runs them, exactly as `AppLaunchRoute.handle` does
(`ActionRegistry.swift:158-161`), so no caller can reach the store without them.

**Rejected alternatives.** A JSON request body — the transport is form-encoded end to end
(`web/index.html:274`, `HTTPRequest.params` at `HTTPParsing.swift:23-32`), and one route does not
get a second body format. Repeated `paths=` fields — `params` is a `[String: String]` dictionary,
so repeats collapse and the wire format cannot express it without changing admission. A mandatory
trailing separator with count inferred from separators — it works, but a client that forgets the
terminator silently loses its last entry, where `n` turns the same mistake into a `400`. A
different separator — it does not address zero-versus-one at all.

### 4.3 Status vocabulary and error tokens

Exactly **one** new entry in `HTTPConnection.respond`'s reason map (`HTTPServer.swift:110-114`,
which covers 200/400/403/404/405/411/413/414/417/431/500/503): `409: "Conflict"`.

`412` and `428` are deliberately **not** introduced. `409` already denotes "conflicts with the
current state of the target resource", and a missing precondition is a `400` exactly as `/claude`'s
`invalid send value` is today. Existing statuses are not redefined and no new failure class is
invented where the current vocabulary can represent it.

| Status | Meaning | Body: one fixed lowercase token, `text/plain`, no document content |
|---|---|---|
| `200` | saved | full JSON shape (§4.1) |
| `400` | request syntax or product bounds | `invalid-count` · `count-mismatch` · `entry-too-long` · `too-many-keys` · `missing-revision` |
| `409` | the resource's state refuses the write | the current `configuration` value (`malformed`, `unsupported-version`, `unreadable`, `wrong-format`, `unrepresentable`, `too-many-controls`, `legacy-readonly`, `corrupt`), or `stale` for a revision mismatch |
| `500` | commit or recovery failure | `write-failed` · `migration-failed` · `recovery-failed` |
| `503` | lock contended | `busy` |

The body is one token in the same style as `/launch`'s `ok` and `unknown app`, drawn from a single
server-authored table shared with the GET `configuration` field: a state refusal reports the state,
a concurrency refusal reports the concurrency reason. No JSON error shape is invented, and no token
carries document content (ADR-015's error-payload rule). This also replaces today's
`error.localizedDescription` in the `POST /launcher` catch (`main.swift:149`), which is an
uncontrolled string in an otherwise fixed-vocabulary API.

## 5. Client compatibility contract

### 5.1 Client integration (ES5, one file, no framework, no build step)

```js
var cfg = { state: 'unreachable', writable: false, revision: '', text: '' };

var CFG_TEXT = {
  'malformed':           'Config file is damaged. Keys are read-only until it is fixed on the Mac.',
  'unsupported-version': 'Config file is from a newer PhoneDeck. Update the Mac to change keys.',
  'unreadable':          'Config file cannot be read. Keys are read-only.',
  'wrong-format':        'Config file has the wrong shape. Keys are read-only.',
  'unrepresentable':     'This deck cannot be shown on this page. Keys are read-only.',
  'too-many-controls':   'This deck has more than 7 keys. Read-only until it is edited on the Mac.',
  'legacy-readonly':     'Old config cannot be upgraded. Keys are read-only.',
  'corrupt':             'A failed save damaged the config file. Keys are read-only.',
  'migrating':           'Another PhoneDeck is upgrading the config. Read-only for now.',
  'unreachable':         'Cannot read the config from the Mac. Keys are read-only.'
};

function applyConfig(d) {
  cfg.state = d.configuration || 'unconfigured';
  cfg.writable = d.writable !== false;
  cfg.revision = d.revision || '';
  cfg.text = cfg.writable ? '' : (CFG_TEXT[cfg.state] || 'Keys are read-only.');
  var w = $('cfgWarn');
  w.textContent = cfg.text;                    // textContent, never innerHTML
  w.style.display = cfg.text ? 'block' : 'none';
}

function loadKeys() {
  xhr('GET', url('/launcher'), null, function (s, text) {
    var d = null;
    if (s === 200) { try { d = JSON.parse(text); } catch (e) { d = null; } }
    if (!d) { applyConfig({ configuration: 'unreachable', writable: false }); return; }
    launcher = d;                              // full shape: selected AND all
    applyConfig(d);
    renderKeys();
  });
}

function saveError(s, body) {
  var code = (body || '').replace(/^\s+|\s+$/g, '');
  if (code === 'stale' || code === 'missing-revision') return 'Not saved: reload the deck page, then save again';
  if (code === 'busy') return 'Not saved: the Mac is busy, try again';
  if (code === 'too-many-controls') return 'Not saved: this deck has more than 7 keys';
  if (code === 'write-failed' || code === 'recovery-failed') return 'Not saved: the Mac could not write the file';
  return s === 409 || s === 400 ? 'Not saved: keys are read-only on the Mac' : 'Save failed';
}

tap($('editSave'), function () {
  if (!cfg.writable) return toast(cfg.text || 'Keys are read-only');
  var body = 'n=' + draft.length
           + '&paths=' + encodeURIComponent(draft.join('\n'))
           + '&expected=' + encodeURIComponent(cfg.revision);
  xhr('POST', url('/launcher'), body, function (s, text) {
    if (s !== 200) return toast(saveError(s, text));
    var d; try { d = JSON.parse(text || '{}'); } catch (e) { d = null; }
    if (!d || !d.all) return toast('Save failed');
    launcher = d;                              // catalog included: byPath() keeps working
    applyConfig(d);
    renderKeys(); sheet('edit', false); toast('Keys saved');
  });
});
```

Markup and CSS — one element, one rule, and **no change to `layout()`**, which is what keeps the
banner out of the pixel arithmetic ADR-010 complains about:

```html
<div id="cfgWarn"></div>            <!-- inside #stage, sibling of #toast -->
```

```css
#cfgWarn { position: absolute; left: 0; right: 0; bottom: 0; z-index: 9; display: none;
  background: rgba(120,60,0,.92); color: #ffd9a0; font-size: 10px; line-height: 13px;
  padding: 4px 8px; text-align: center; white-space: normal; }
```

`white-space: normal` is the point of F2 — `#toast` cannot wrap. `z-index: 9` sits above the keys
and below `.scrim` (10, `web/index.html:136`), so the editor sheet covers the banner and carries
its own explanation in the element that already exists: `renderEditor()` prefixes `#editCount` with
`cfg.text`.

Three properties worth naming. `!d.all` is a hard guard, so a future response that drops the
catalog fails loudly instead of rendering seven "Add" keys. `cfg.revision` is refreshed from every
response, which is what makes a second edit work without another GET. And `loadKeys()` no longer
returns silently on a non-200 (`web/index.html:410`) — an unreachable configuration is a visible
read-only state rather than an empty deck. The client-side guard is a courtesy; the server's `409`
is the control, and a hand-rolled client that skips the guard still cannot write.

### 5.2 Old and new clients

| Client | Behaviour |
|---|---|
| **Pre-M2.5 page, already loaded on the phone — reading** | Ignores every new field. `selected` array → renders; `null` → seven "Add" keys. Identical to today, **including the silent-empty-deck failure mode**. Not fixable retroactively. |
| **Pre-M2.5 page, already loaded — saving** | Sends no `expected` → `400 missing-revision`, nothing written, and the old client shows its existing `toast('Save failed')` (`web/index.html:478`). **Fails loudly, never silently.** One page reload fixes it; `Cache-Control: no-store` (`HTTPServer.swift:117`) guarantees the reload fetches the M2.5 client. |
| **Pre-M2.5 binary against a migrated directory** | Reads `launcher.json`, casts to `[String]`, serves the pre-migration selection. Writes only on POST, and only to `launcher.json`. See §7.4. |
| **M2.5 page against a pre-M2.5 server** | Cannot occur: the page is served by the binary. Defensively, `writable` absent → treated as writable, `revision` absent → `expected=` → the server's `400`. No JS error either way. |

Revision 2's claim that an already-loaded pre-M2.5 page "degrades to exactly today's behaviour" is
**withdrawn for the save path** and replaced by the second row above. This is the one user-visible
regression M2.5 introduces, and it is a refusal rather than a loss.

## 6. Revision token

Revision 2's rule compared `config.json` bytes between classification and lock acquisition. That
window is milliseconds wide and inside one request; the window that matters is the browser's,
minutes wide, between its GET and its POST. The byte rule is withdrawn and replaced.

### 6.1 Definition

The revision is an opaque fingerprint of the **configuration content the client observed** — not of
file bytes, and not of anything inside the V1 document, so the codec and schema are untouched.

```
revision = lowercase hex, 16 chars, of  fnv1a64( tagByte ‖ payload )

tag 'v'  payload = ConfigurationCanonicalForm.data(c)   every state with a V1 denotation
tag 'c'  payload = raw bytes of config.json             damaged / wrongFormat, config source
tag 'l'  payload = raw bytes of launcher.json           damaged / wrongFormat / unrepresentable, legacy source
```

For `unconfigured` the payload is the canonical encoding of `DeckConfigurationV1(controls: [])`,
computed at runtime — the exact pretty-printing is never hardcoded and no test asserts a literal
token. For `migrationPending` it is the canonical encoding of `migrateToV1(paths)`, which by F9 is
the exact `Data` the commit will write.

If `ConfigurationCanonicalForm.data` returns `nil` (unreachable for a document that just decoded),
no revision is published and the state is read-only.

### 6.2 Why a 64-bit non-cryptographic fingerprint

The token is a **concurrency control, not an integrity or authentication control**. A client
holding the access token can always GET a fresh revision and then write anything it likes; the
token exists to stop an *accidental* stale overwrite, which is the same job an `If-Match` ETag does
in a single-user application. Cryptographic strength therefore buys nothing, and a 64-bit
fingerprint avoids adding CryptoKit or CommonCrypto to a project whose framework list is
deliberately short (AGENTS.md §4). A collision means one accepted stale write at roughly 2⁻⁶⁴ per
document pair. The token is opaque: the client stores it, echoes it, and must never parse it.

### 6.3 Revision by state

| State | Tag / payload | Published | Note |
|---|---|---|---|
| `ready`, `overLimit`, `unprojectable` | `v` / canonical bytes | yes | whitespace-only hand edits do **not** change it — content identity, not byte identity |
| `migrationPending` | `v` / canonical bytes of `migrateToV1(paths)` | yes | equals the post-migration revision |
| `unconfigured` | `v` / canonical bytes of the empty V1 document | yes | fixed and deterministic |
| `legacyUnrepresentable` | `l` / raw `launcher.json` bytes | yes | read-only; published for diagnostics |
| `damaged(.config)`, `wrongFormat(.config)` | `c` / raw bytes | yes | a repair changes it |
| `damaged(.legacy)`, `wrongFormat(.legacy)` | `l` / raw bytes | yes | |
| `corrupt` | `c` / raw bytes | yes | read-only |
| `busy` / `migrating` | — | **no** | never publish a token you cannot honour |

### 6.4 Migration transitions

The property falls out of §6.1 rather than needing a special case:

- **Before migration** (`migrationPending`): fingerprint of `canonical(migrateToV1(paths))`.
- **After migration** (`ready`): fingerprint of `canonical(decoded config.json)` — and the committed
  bytes *are* `canonical(migrateToV1(paths))`, because `verifiedData` returns
  `ConfigurationCanonicalForm.data(configuration)` unchanged (F9).

The two are identical, so **migration does not invalidate a client's revision**, and correctly so:
migration is lossless (ADR-015 rule 4), so a browser that read the legacy selection and then saves
is not overwriting anything it did not see. A byte-comparison rule would have rejected this
legitimate save as a false conflict; a raw-bytes fingerprint would too.

Where migration fails to commit, the state stays `migrationPending` and the revision is unchanged,
so a retry needs no re-GET. Where another process migrates concurrently, the loser adopts the
winner's document (§3.2) and the revision is the winner's — identical to its own by the argument
above.

### 6.5 Validation

`expected` is compared against the revision recomputed **under the exclusive lock**, after
re-classification. Precedence is fixed so the client always receives the most actionable refusal:

```
400 syntax / bounds        validateParameters, pre-handler, no I/O
503 busy                   LOCK_NB failed
409 <state token>          re-classified state is not writable, including too-many-controls
400 missing-revision       expected absent or empty
409 stale                  expected != revision computed under the lock
500 write-failed           build, commit or recovery failure
```

State before revision, because "reload the page" is useless advice when the file on the Mac is
damaged. The revision check subsumes the withdrawn byte comparison: the in-lock re-read now
classifies the state, which covers both the absent→present transition and any concurrent write
with one mechanism instead of two.

## 7. Write and recovery algorithm

Revision 2a specified `unlink(config.json.prev)` followed by `link(config.json, config.json.prev)`,
which destroyed the good backup before knowing the replacement could be created. It also placed
the backup swap *after* the commit while its failure table described that swap as a pre-commit
failure. Both are corrected here: **the backup is prepared under a temporary name and swapped in by
`rename` before the commit, so an existing backup stays visible and byte-intact until its successor
exists, and recovery restores the generation the client's revision actually described.**

```
PREPARE — nothing on disk has changed
 P1  validateParameters: n / paths agreement, entry length, expected present          -> 400
 P2  c    = ConfigurationMigrator.migrateToV1(paths)     // one builder for save and migration
     data = ConfigurationEncoder.verifiedData(c)                                       -> 500 write-failed
 P3  flock(config.lock, LOCK_EX | LOCK_NB)                                             -> 503 busy
 P4  re-read config.json and launcher.json (O_NOFOLLOW, fstat, S_ISREG, bounded); re-classify
       baseBytes = config.json's exact bytes, or nil if it does not exist
       baseValue = the decoded V1 of baseBytes, or nil
       state not writable                            -> 409 <state token>
       expected != revision(state)                   -> 409 stale
 P5  tmp = mkstemp("config.json.tmp-"); fchmod 0600; write data; fsync(tmp); close
       fail -> unlink tmp; 500 write-failed; config.json and .prev untouched
 P6  if baseBytes != nil:
       tmpLink = link(config.json, "config.json.prev.tmp-<mkstemp suffix>")
                 copy fallback (bounded read -> tmp -> fsync) if link fails EPERM/EXDEV/EOPNOTSUPP
       fsync(dirfd) best-effort
       fail -> unlink tmpLink and tmp; 500 write-failed;
               config.json intact AND config.json.prev intact and byte-identical
     else tmpLink = nil                                  // initial write: no previous generation

COMMIT
 C1  if tmpLink: rename(tmpLink, config.json.prev)   // atomic backup swap; .prev := base generation
       fail -> unlink tmp and tmpLink; 500 write-failed; config.json intact (still base);
               config.json.prev untouched, still the older generation
 C2  rename(tmp, config.json)                        // ATOMIC REPLACEMENT
       fail -> unlink tmp; 500 write-failed; config.json intact (base); .prev == base (a duplicate)
 C3  fsync(dirfd)                                    // best-effort; any errno swallowed

VERIFY
 V1  re-open config.json (O_NOFOLLOW), bounded read, decode; require .v1(c') && c' == c
       pass -> 200 full shape, revision = fingerprint(canonical(c))

RECOVER — only on V1 failure, and from baseBytes captured at P4, not from .prev
 R1  baseBytes != nil:
       tmp2 = mkstemp; write baseBytes; fsync(tmp2); rename(tmp2, config.json); fsync(dirfd) best-effort
       re-verify == baseValue
         pass -> 500 write-failed      restored the generation the client's revision described
         fail -> 500 recovery-failed   state = corrupt; writable = false; nothing deleted
 R2  baseBytes == nil (initial migration):
       -> 500 migration-failed
          config.json is NOT deleted — it is the only evidence and the only generation
          state = corrupt; writable = false
          GET reports "corrupt" with selected: null — never "migrated"
          documented manual recovery: remove the damaged config.json; launcher.json is frozen and
          byte-intact, so the next GET re-migrates from it

UNLOCK — defer, on every path
```

### 7.1 Why recovery reads `baseBytes` and not `.prev`

The document that must be recoverable is the one whose revision the client echoed. `baseBytes` is
captured at P4 under the lock and is by construction exactly that document, so recovery does not
depend on the backup swap at C1 having succeeded, on hard links being supported, or on `.prev`
being fresh. `.prev` remains the **durable, cross-restart** copy of the same base generation; after
C1 the two always agree. Damaged configuration is never auto-restored at startup — a damaged
`config.json` is read-only with `.prev` available for manual recovery, because a silent fallback to
any other file is exactly what R1 forbids.

### 7.2 Failure and recovery matrix

| Class | Point | Response | `config.json` | `config.json.prev` | Temps | State after |
|---|---|---|---|---|---|---|
| pre-commit | P1 syntax | `400` | untouched | untouched | none | unchanged |
| pre-commit | P2 build / `verifiedData` | `500 write-failed` | untouched | untouched | none | unchanged |
| pre-commit | P3 lock | `503 busy` | untouched | untouched | none | unchanged |
| pre-commit | P4 state | `409 <state>` | untouched | untouched | none | unchanged |
| pre-commit | P4 revision | `409 stale` | untouched | untouched | none | unchanged |
| pre-commit | P5 temp | `500 write-failed` | untouched | untouched | unlinked | unchanged |
| pre-commit | P6 backup link | `500 write-failed` | untouched | **intact, byte-identical** | both unlinked | unchanged |
| pre-commit | C1 backup swap | `500 write-failed` | untouched (base) | untouched (older generation) | both unlinked | unchanged |
| pre-commit | C2 commit rename | `500 write-failed` | base | base (duplicate) | tmp unlinked | content unchanged |
| post-commit | C3 dir sync fails | **`200`** | new | base | none | new |
| post-commit | V1 verify fails, recovery ok | `500 write-failed` | base (restored) | base | tmp2 consumed | base |
| post-commit | V1 verify fails, recovery fails | `500 recovery-failed` | damaged, retained | base, retained | retained | `corrupt`, read-only |
| initial write | V1 verify fails | `500 migration-failed` | damaged, retained | never existed | none | `corrupt`, read-only |
| crash | between P5 and C1 | — | base or absent | older or absent | one leaked tmp | unchanged; leaked temp inert |
| crash | between C1 and C2 | — | base | base (duplicate) | one leaked tmpLink | unchanged; distinctness restored by the next successful write |
| crash | after C2, before C3 | — | new, possibly non-durable | base | none | may read as `corrupt` after power loss |
| any | leaked temp after a crash | — | unaffected | unaffected | `config.json.*.tmp-*` | inert: no code path reads it |

C1 before C2 is deliberate. At the moment recovery is needed, `.prev` is guaranteed to be the base
generation, and the only crash window leaves `.prev` *duplicating* `config.json` — harmless —
rather than leaving it a generation behind, which would make a later recovery restore a document
the client never saw.

### 7.3 Failure classes the design must keep distinct

| Class | Meaning | Client sees |
|---|---|---|
| Failure **before** commit | nothing became visible | `400` / `409` / `503` / `500 write-failed`; state unchanged |
| Failure **after** commit, recovery **succeeded** | the edit did not take effect; the base generation is live again | `500 write-failed`; follow-up GET reports `v1` with the base revision |
| Failure after commit, recovery **failed** | the document is damaged and both files are retained | `500 recovery-failed`; follow-up GET reports `corrupt` |
| **Initial migration** with no previous V1, verify failed | the only generation is damaged; retained as evidence | `500 migration-failed`; follow-up GET reports `corrupt`, never `migrated` |

### 7.4 Accepted residual: downgrade

A pre-M2.5 binary reads `launcher.json` with `as? [String]` (`Control.swift:73`) and, on POST,
rewrites it. After cutover it therefore serves the **pre-migration** selection, cannot see later
edits, and is not prevented from writing. Mitigating this would mean writing `launcher.json` again,
which the approved "legacy file retained unchanged, no permanent dual-write" direction excludes.
The cost is disclosed, rehearsed in §12 Phase D, and accepted.

## 8. Writable-state rules

`writable == true` requires **all** of:

1. the state has a V1 denotation — `ready`, `unconfigured` or `migrationPending`;
2. `ConfigurationMigrator.legacySelection(v1) != nil` — no title, no custom or gapped id, no
   unregistered action, no `.unmodeled` parameters;
3. `v1.controls.count <= 7`;
4. `config.json` is absent or a regular file — not a symlink, FIFO or directory;
5. the lock was acquirable for this response.

Checks are ordered 2 then 3, so a titled nine-control document reports `unrepresentable`;
determinism matters more than which of two read-only reasons is more actionable, and the same
banner surfaces both.

Condition 3 closes a hole revision 2 left open: a document of 8+ pure `app.launch` controls
satisfies 1 and 2, so it was marked writable, while the editor's
`draft = (launcher.selected || []).slice(0, APP_SLOTS)` (`web/index.html:443`) silently drops
everything past the seventh on save. Condition 3 does **not** truncate, filter or repair: the
document is served in full and left byte-identical.

`writable` is a prediction. The server re-evaluates every condition under the lock, and a
`false` prediction can only cost a refused save, never a lost one. Condition 5 in particular is
per-response: a contended read reports `migrating` with no revision and `writable: false`.

## 9. File layout

```
~/.oldphonedeck/                        (or --config-dir PATH; created 0700 when new)
├── token                    0600   unchanged; loadToken() untouched
├── config.json              0600   NEW — authoritative V1 document
├── config.json.prev         0600   NEW — exactly one retained previous generation (hard link)
├── config.json.tmp-XXXXXX   0600   NEW — mkstemp temp; same directory, so rename is same-filesystem
├── config.json.prev.tmp-XXX 0600   NEW — pending backup replacement; renamed into place or unlinked
├── config.lock              0600   NEW — flock target; empty; created idempotently; never read
├── launcher.json            0644   FROZEN — legacy array; read-only; never written or deleted
└── tls/                     —      unchanged contents; location follows --config-dir
```

Mode `0600` for `config.json` is a deliberate departure from `launcher.json`'s `0644`
(ARCHITECTURE §10): a new file with no compatibility constraint, written via `fchmod` on the fd so
umask cannot widen it, with `.prev` and temps inheriting it. `config.lock` is a separate file
rather than a lock on `config.json` itself, because `config.json` may legitimately be absent and its
inode is replaced on every write — a lock on a replaced inode locks nothing.

Shared paths that `--config-dir` does **not** redirect, stated exhaustively:

| Shared | Where | Effect on an isolated instance |

| `/Applications`, `/Applications/Utilities`, `/System/Applications`, `/System/Applications/Utilities`, `~/Applications` | `Control.swift:19-22` (`Apps.list`) | Real app catalog. Reads only. |

## 10. Temporary file safety

1. **`mkstemp(3)`**, never a PID-derived name. It performs `O_CREAT|O_EXCL|O_RDWR` with a random
   suffix and mode `0600`, so it cannot collide with, predict or open another process's file.
2. `fchmod(fd, 0600)` explicitly after creation, because the guarantee must not be implicit.
3. Created **in the target's own directory**, which is what makes the rename same-filesystem;
   `EXDEV` is therefore unreachable, and the directory path is used as resolved so a symlinked
   `~/.oldphonedeck` cannot split temp and target across volumes.
4. **Ownership:** a temp file belongs to the process that created it and is unlinked by that
   process on every failure path via `defer`. On success a rename consumes it.
5. **No glob-based startup deletion.** Nothing at startup enumerates or removes files it did not
   create: a second live instance may be mid-write, and a sweep would delete its temp out from
   under it. A leaked temp is inert — no code path reads `config.json.tmp-*` or
   `config.json.prev.tmp-*`.
6. Optional narrow reap (U5, resolved against): only while holding the exclusive lock, which proves
   no live writer exists, unlink entries matching an exact prefix with an mtime older than 7 days,
   never touching `config.json` or `config.json.prev`. **Not implemented in M2.5** — no code path
   reads the temps, writes are rare user actions, and the reap would add a deletion path to a slice
   whose whole subject is not deleting things. Manual cleanup is documented instead.

## 11. Concurrency and durability policy

### 11.1 Serialization

| Scope | Mechanism | Why it suffices |
|---|---|---|
| Intra-process | The shared serial HTTP queue (`main.swift:69,186`) | F7: all request handling on both listeners is already serialized. No config access happens on the media (`PhoneMedia.swift:9`), stats or music queues, and none is added. |
| Cross-process | `flock(LOCK_EX \| LOCK_NB)` on `config.lock`, held across the whole read-modify-write including migration-on-read | A separate long-lived lock file, so it survives `config.json`'s inode being replaced. |
| Waiting | **None.** Contention → `503` for a write, read-only response for a migration | R5: any wait blocks MJPEG delivery on the same queue. |
| Lock unavailable | Fail closed: read-only, never write without the lock | A write that cannot be serialized is a write that can lose an update. |

`flock` locks belong to the open file description, so two fds in one process also conflict: the
policy is uniform whether the second writer is another thread or another process. Locks are
released by the kernel on process death, so a crash cannot leave the configuration permanently
locked.

### 11.2 Atomic visibility is not durability

- **Atomic visibility** comes from `rename(2)` within one filesystem: any reader sees the complete
  old document or the complete new one, never a prefix and never a gap. On APFS the
  directory-entry replacement is additionally journaled, so it survives a crash as an
  all-or-nothing event. This is why readers need no lock.
- **Durability** is a separate claim the rename does not make. Without `fsync(fd)` before the
  rename, the new inode's data may not have reached stable storage when the entry becomes visible;
  after a kernel panic or power loss the file can exist and be empty or torn. Without a directory
  sync the entry itself may not survive.
- **Residual, stated plainly:** an acknowledged `200` can still be lost on power failure. For a
  seven-key layout on a desk Mac that is proportionate (U4, resolved: `fsync` only).
- **`launcher.json` is not a backup.** After migration it holds the pre-migration selection
  forever and cannot recover a single later edit. `.prev` plus `fsync` is the recovery mechanism,
  and `.prev` holds exactly one generation, so two consecutive failed saves can lose a good
  document. The single exception is a failed **initial** migration, where `launcher.json` is
  byte-intact precisely because migration never writes it (§7, R2).

### 11.3 Directory fsync — measured, not assumed

`fsync` on a directory fd is the Linux idiom for persisting a rename. On macOS `open(dir, O_RDONLY)`
succeeds and `fsync(dirfd)` is generally accepted, but Apple documents no guarantee that it flushes
directory metadata, and `F_FULLFSYNC` on a directory fd returns `EINVAL`. The design must not
depend on the answer, and S1 must measure it:

- **File-data sync is pre-commit and fatal.** `fsync(tmp)` failing means the bytes may be wrong and
  nothing is visible yet → unlink, `500 write-failed`, zero on-disk consequence.
- **Directory sync is post-commit and best-effort.** Any errno from `fsync(dirfd)` — including
  `EINVAL`, `ENOTSUP`, `EBADF` — is swallowed. A save is never failed for it, and no client-visible
  token changes, because the rename has already succeeded and undoing it would be worse.
- **`F_FULLFSYNC` is used nowhere:** tens of milliseconds on the one serial queue that also carries
  MJPEG.
- S1 ships two measurement tests: one creating a temp directory, opening it `O_RDONLY`, calling
  `fsync` and recording 0 or the observed errno on this build; one hard-linking a file inside a temp
  directory to confirm `link(2)` works on APFS, with the copy fallback exercised separately by
  injection. If directory `fsync` proves unsupported, the ADR's durability sentence is amended to
  say so — the algorithm does not change.

### 11.4 Bounded blocking

On `server.queue` every operation is bounded: `LOCK_NB` with no wait and no retry sleep; reads
capped at `maximumDocumentBytes + 1`; the revision fingerprint bounded by the same 1 MiB cap; the
recovery write of `baseBytes` bounded likewise; no `F_FULLFSYNC`. The worst case is one canonical
re-encode plus a handful of syscalls on a ≤1 MiB document, against a catalog scan that
`GET /launcher` already performs.

Dispatching the write off-queue and hopping back — the pattern `/icon` uses
(`main.swift:154-157`) — was considered and rejected: it would remove the intra-process
serialization R3 relies on, forcing the lock to carry correctness the queue gives for free.

## 12. Isolated acceptance protocol

### 12.1 Design of the option

`--config-dir PATH` (R14), resolved to an absolute path, governing `token`, `config.json`,
`config.json.prev`, temps, `config.lock` and `tls/`. Default unchanged. The startup banner gains
one line naming the configuration directory in use, so isolation is visible rather than assumed.

**TLS: copy, do not share.** The isolated directory receives a `cp -p` copy of the real `tls/`,
preserving modes. This keeps the CA the iPhone 11 **already trusts** — no new profile, no new trust
decision, no human dialog — while ensuring the test instance can never rewrite the real
`server.p12` or `server.ip`. Sharing `tls/` in place is rejected: `LocalTLS.identity(for:)`
re-issues whenever `tls/server.ip` differs from the current LAN IP (`TLS.swift:19-21`), so a test
instance started after an IP change would silently replace the production identity.

**Token: isolate.** The isolated directory starts with no `token`, so `loadToken()` mints a fresh
one (`main.swift:34-42`) and the real token is never read by the test process. The isolated token is
a throwaway scoped to a directory deleted at teardown, and the phone's `localStorage` is
origin-scoped, so `:8057` cannot clobber the `:8047` token. U2 resolved: the agent may display the
isolated URL, labelled throwaway.

### 12.2 Protocol

The agent runs every terminal step; the human only touches the phone (ADR-013).

**Phase A — staging, no device.**
1. `swift build -c release` from the branch; record zero warnings.
2. Record SHA-256 of the real `~/.oldphonedeck/launcher.json`, `token` and every file in `tls/`,
   plus mtimes. Hashes go in the run log; the token's **content** is never printed.
3. `mkdir -m 700 ~/.oldphonedeck-acceptance-m2.5`; `cp -p ~/.oldphonedeck/tls` into it.
4. Confirm `tls/server.ip` equals the current LAN IP, so neither directory re-issues.
5. Seed the isolated `launcher.json` with a copy of the real one, or with a fixture if Steering
   prefers not to duplicate real paths. This is the only place real configuration content is
   copied, into a 0700 directory the same user owns.
6. Start `./.build/release/oldphonedeck --port 8055 --config-dir ~/.oldphonedeck-acceptance-m2.5`,
   banner redirected to a `0600` log. Ports follow the established acceptance triple: **8055 HTTP /
   8057 HTTPS / 8058 WSS**. The real 8045/8047/8048 instance is never stopped.
7. Assert the banner names the isolated directory.
8. **Prove isolation before involving the phone:** one authenticated `GET /launcher` against
   `:8055`; assert an isolated `config.json` now exists, `configuration: "migrated"`, and that the
   real directory's hashes and mtimes are unchanged.

**Phase B — device acceptance, iPhone 11.**
9. Human opens `https://<lan-ip>:8057/#k=<isolated token>` — the **8057** URL, because the page
   derives its WSS port from its own port; a page from 8047 streams to 8048 and the test instance
   sees nothing.
10. Deck renders the migrated keys; no banner. Landscape and portrait, plus Home Screen standalone
    (ADR-002).
11. Hold a key → editor → change one app → Save → `Keys saved`, no banner, **and the icons still
    render after the save** (the Issue-A regression, on real hardware). Verify on the Mac that the
    isolated `config.json` changed and `config.json.prev` exists.
12. Edit and save a **second time without reloading**, to prove the POST response refreshed
    `revision`.
13. Preservation: seed a path to a nonexistent `.app` and assert it survives a save in
    `config.json` — the F4/R10 proof.
14. **Failure states on the device.** Stop the instance; append a trailing comma to the isolated
    `config.json` (the strict scanner rejects it, ADR-015 rule 6); restart; reload → amber banner,
    Save refused, clock/media/Internet widgets unaffected. Then `"version": 2` → banner says
    upgrade. Then an 8-control document → banner says more than 7 keys and Save is refused. Then
    restore from `.prev` → banner gone, keys back.
15. **Stale revision on the device.** Load the page in two Safari tabs; save from one; save from the
    other → `Not saved: reload the deck page, then save again`; reload → save succeeds.
16. **Concurrency, no device.** Start a second instance on `--port 8065` against the *same*
    isolated directory; fire interleaved GET/POST at both; assert no `500`, no torn document, and
    that a contended write returned `503` rather than blocking.

**Phase C — teardown.**
17. Stop both instances; delete the isolated log and directory; re-verify every hash and mtime from
    step 2. Record the output as evidence the production configuration was never touched.

**Phase D — production cutover, separately authorized.** Nothing in Phases A–C authorizes this.
18. Copy the real `launcher.json` to a dated backup outside the config directory; record SHA-256.
19. Stop the 8045 instance; start the M2.5 binary on 8045 with **no** `--config-dir`; one
    `GET /launcher` to trigger migration.

21. **Reload the deck page on the iPhone before the first post-cutover save** (§5.2). An

## 14. Regression test scenarios

All five run over a loopback `HTTPServer(port: 0)` with production `DeckRoute.admit`/`match` in
front of the shared `LauncherRoute.handle` (F8, S1b), over a temp config directory
(`TLSResourceTests.swift:9-11`). The catalog is injected, so no test can reach `NSWorkspace`, and no
test constructs a production `ActionRegistry()` — both conditions Codex required in M2.3.

### T-A — GET → edit → POST → render → edit again
**Arrange:** temp dir seeded with a 3-path `launcher.json`; fake catalog of 6 apps.
**Act/Assert:** GET → `all.count == 6`, `selected.count == 3`, `revision` non-empty. Model the
editor (`draft = selected.slice(0,7)`, drop one, add one). POST with `n`, `paths`, `expected`.
Assert `200` and, on the response: **`all` present and equal to the GET's `all`**,
`selected == draft`, `revision` differs from the GET's, `configuration == "v1"`. Model `renderKeys`
with a helper mirroring `byPath` over `selected` × `all`, and assert the rendered app count equals
`draft.count`. Then **edit again using only the POST response, with no second GET**, and assert
`200`.
**Mutations that must turn it red:** omitting `all` from the POST response (rendered count collapses
to 0); retaining `launcher.selected = draft.slice()` on the client while the server filtered (the
`selected == draft` assertion fails); not returning the new `revision` (the second save fails).

### T-B — revision lifecycle
B1 **stale**: GET (rev X); a second store instance commits rev Y; POST with X → `409 stale`,
`config.json` byte-identical to Y, `.prev` untouched.
B2 **missing/empty**: POST with no `expected` → `400 missing-revision`; with `expected=` → same;
bytes unchanged in both.
B3 **current**: POST with Y → `200` and a new revision ≠ Y.
B4 **migration transparency**: GET while `migrationPending` → rev R; a second store commits the
migration; POST with R → **`200`, not `409`**.
B5 **stability**: two GETs with no intervening write → identical revision.
B6 **distinctness**: `unconfigured` ≠ one-control; the same raw bytes under tag `c` and tag `l`
differ; a whitespace-only reformat of `config.json` leaves the revision **unchanged**.
B7 **precedence**: a damaged `config.json` plus a missing `expected` → `409 malformed`, not
`400 missing-revision`.
B8 **contended read publishes no token**: with the lock held externally, GET → `configuration:
"migrating"`, `writable: false`, and **no `revision` key at all**.
**Mutations:** fingerprinting raw bytes instead of canonical bytes → B4 and B6 red; dropping the
in-lock recomputation → B1 red; dropping the state-before-revision ordering → B7 red; publishing a
revision on a contended read → B8 red.

### T-C — 8 controls must not become 7
**Arrange:** write a `config.json` of 8 `app.launch` controls, ids `app-1…app-8`, via
`ConfigurationEncoder`.
**Assert on GET:** `selected.count == 8` (untruncated), `writable == false`,
`configuration == "too-many-controls"`, `revision` present. Model the editor's
`slice(0, APP_SLOTS)` and assert the eighth path is in `selected` but absent from `draft` — the
exact truncation the server must refuse.
**Assert on POST** of those 7 paths with the correct revision: `409 too-many-controls`,
`config.json` byte-identical, still decoding to 8 controls, `.prev` untouched.
**Control:** a 7-control document is writable and saves with `200`.
**Mutation:** removing condition 3 from the writable rule → the POST returns `200` and the file
holds 7 controls → red.

### T-D — wire round-trip
Table-driven over every row of §4.2's table. For each accepted case, assert the stored V1
document's `.appPath` values equal the input element-for-element **in order**, including empty
strings and duplicates, and that a follow-up GET returns the same array. Also: a 4096-byte path
accepted, a 4097-byte path → `400 entry-too-long`.

Rejected, with nothing written and `config.json` byte-identical in every row:
`n=0 & paths=/A.app` · `n=1 & paths=/A.app\n/B.app` · `n=2 & paths=/A.app` ·
`n=2 & paths=\n\n` (three elements) · `n=8` · `n=+1` · `n=01` · `n=1.0` · `n=x` · `n=" 1"` ·
`n=` (present but empty).

**Accepted, and the row revision 2a got wrong:** `n=1 & paths=` → **one control holding
`.appPath("")`**. This is the one-empty-path case, and it is the entire reason `n` exists; treating
it as a mismatch would reintroduce the zero-versus-one ambiguity the parameter was added to remove.

Legacy branch (no `n`): `paths` absent → 0 controls; `paths=""` → 0 controls;
`paths="a\n\nb"` → 2 controls, reproducing `main.swift:147` exactly.
**Mutations:** reverting to `omittingEmptySubsequences: true` → the `[""]`, `["/A.app",""]` and
`n=1 & paths=` rows red; removing the `n`-agreement check → `n=1 & paths=/A.app\n/B.app` silently
stores one control → red; treating an empty `n` as absent → the `n=` row red.

### T-E — deterministic failure injection
The store takes an injected filesystem seam defaulting to the real POSIX implementation, mirroring
`ActionRegistry.init(approvedAppPath:launchApp:)` (`ActionRegistry.swift:99-102`) and
`AppLaunchExecutor.schedule(launch:)`. Each injection fails one named step once. Every row asserts
five things: HTTP status and body token, the exact bytes of `config.json`, the exact bytes of
`config.json.prev`, the set of leftover `*.tmp-*` entries, and the `configuration` value of a
follow-up GET.

| Injection | Expected |
|---|---|
| `tempCreate`, `tempWrite`, `tempSync` | `500 write-failed`; temp unlinked; both files byte-identical |
| **`backupLink`** | `500 write-failed`; **pre-existing `.prev` present and byte-identical**; `config.json` untouched |
| `backupRename` (C1) | `500 write-failed`; `config.json` untouched (still base); `.prev` untouched (still the older generation); both temps unlinked |
| `commitRename` (C2) | `500 write-failed`; `config.json` untouched; `.prev` now duplicates it |
| `dirSync` (P6, C3) | **`200`** — best-effort; the errno never surfaces (§11.3) |
| `verifyRead` corrupt, base exists | `500 write-failed`; restored **from `baseBytes`**; follow-up GET `v1` with the base revision |
| `verifyRead` corrupt, **initial migration** | `500 migration-failed`; `config.json` retained, not deleted; follow-up GET `corrupt`, `selected: null`, `writable: false`; `launcher.json` byte-identical; **no response, log or state ever reports `migrated`** |
| `recoveryRename` | `500 recovery-failed`; both files retained; follow-up GET `corrupt`; nothing deleted |
| `linkUnsupported` (forces the copy fallback) | `200`; `.prev` holds the base bytes by copy rather than by inode |
| platform: `open(dir,O_RDONLY)` + `fsync`; `link(2)` in a temp dir | return 0 on this build, or the observed errno is recorded — measurement, not assumption |

**Mutations:** restoring the `unlink(.prev)` → `link(...)` order → the `backupLink` row red (the good
backup is gone); moving C1 after C2 → the `backupRename` and `verifyRead` rows red, because recovery
would restore a generation older than the one the client saw; reporting `200` after a failed verify
→ both `verifyRead` rows red; falling back to `launcher.json` when `config.json` is damaged → the
`corrupt` assertion red; recovering from `.prev` instead of `baseBytes` with C1 failed → red.

## 16. Resolved decisions

| # | Question | Resolution |
|---|---|---|
| U1 | Is `--config-dir` permanent product surface? | **Resolved: permanent**, documented in `--help` and README. It is the only way to make storage testable here, and it is also the recovery tool for a damaged production directory. |
| U2 | May the agent display the isolated instance's throwaway `#k=` URL? | **Resolved: yes, labelled throwaway.** It authorizes only a test instance in a directory deleted at teardown, and the real token is never read. A deliberate, narrow departure from the habit of never printing a tokenised URL. |
| U3 | Approve narrowing the ARCHITECTURE §9 control "re-filtering of config on save"? | **Resolved: approved.** Storage of an unapproved path is inert; `Apps.isKnown` still gates every launch and every icon. Preservation is otherwise impossible. |
| U4 | Durability level: `fsync` only, or `F_FULLFSYNC` on the migration write? | **Resolved: `fsync` only.** The migration write is not more valuable than a save, and the stall lands on the MJPEG queue. |
| U5 | Implement the narrow leaked-temp reap? | **Resolved: no.** No code path reads the temps; manual cleanup is documented instead (§10.6). |
| U6 | Should GET expose `"limit": 7`? | **Resolved: no, not in M2.5.** Consuming it means changing `renderKeys`/`renderEditor` loop bounds — ADR-010's data-driven frontend, which is M3. The duplication is documented. |
| U7 | For `wrongFormat`, report only or auto-repair? | **Resolved: report only.** Auto-adoption is a mutation the user did not request and is undefined when both files hold documents. |
| U8 | Is the `configuration` vocabulary final, and is `writable` the right client guard? | **Resolved with an addition:** the vocabulary is accepted and `writable` remains the guard, **and** a client revision contract is required alongside it (§6). `revision` is published by GET, echoed as `expected` by POST, and validated under the lock. |

## 17. Remaining material blockers

1. **`LauncherRoute.handle` must be extracted** from `main.swift`'s top-level `routes` closure
   (F8, S1b). Without it, T-A, T-B and T-D cannot exercise production wiring, and the M2.3
   principle that "a test cannot pass against wiring production does not use" would be violated.
2. **A filesystem-injection seam is required** for T-E's deterministic failure tests. It follows
   the injecting-initializer idiom reviewers accepted in M2.3, but it does mean
   `ConfigurationStore` is not a plain value type.
3. **Steering must explicitly accept the pre-M2.5 save regression** (§5.2, C-8). Rev. 2's
   compatibility claim is corrected, and Phase D gains a reload step.
4. **The macOS directory-`fsync` measurement gates the ADR's durability wording, not the design**
   (§11.3). If `fsync(dirfd)` returns `EINVAL` on this build, ADR-016 rule 8 must say so.
5. **Status vocabulary confirmation.** One new reason-map entry (`409`) and one new error-token
   table; `412`/`428` deliberately avoided in favour of the existing vocabulary. If Steering prefers
   standards-exact precondition statuses over contract stability, that changes both the reason map
   and the client's `saveError` mapping and must be decided before S3.

Non-blocking, recorded: the revision token prevents lost updates, not user error, and a hostile
token-holder can always refresh it (§6.2); `revision` is withheld on a contended read, so a client
that loads during contention must re-GET before saving; a whitespace-only hand edit is invisible to
the revision by design (§6.3, T-B6); and `.prev` holds one generation, so two consecutive failed
saves can lose a good document (§11.2).
