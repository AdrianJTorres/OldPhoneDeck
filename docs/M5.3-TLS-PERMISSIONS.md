# M5.3-S2 — TLS private material

Base: `ae9cbf3b73334cd5ca8c229382375e1f6aeab554`. Implementation candidate;
merge, production permission remediation and deployment remain separate Steering gates.
The existing single-bearer model is provisionally accepted for this slice.

`ca.key`, `server.key` and `server.p12` must be nonempty regular files owned by the
process user, mode exactly `0600`, with one link and no extended ACL. Reads use
`O_NOFOLLOW | O_NONBLOCK` and `fstat`; PKCS#12 import reads the validated descriptor.
The TLS directory must belong to that user, have no symlink/extended ACL and no
group/other write access. Existing `0755` TLS directories remain valid. Configuration
paths and their ancestors remain trusted local administration; malicious same-user
processes are outside this boundary.

Private outputs are exclusively reserved at `0600` and checked before any producer
writes, then checked afterwards. Only a newly created empty inode may be `fchmod`ed.
OpenSSL writes into that inode: no process-wide umask change or post-write repair.
Public certificate modes, PKCS#12 format/password, CA chain, ports and APIs are unchanged.
Normal and managed existing-only loads reject unsafe/incomplete private material without
chmod or regeneration. Managed startup validates all three secrets before listeners.
A complete secure identity retains normal unmanaged IP-change reissue behavior;
managed startup still refuses changed IP. Only an empty TLS directory is fresh: a retained
public CA, auxiliary file or unexpected remnant also prevents automatic regeneration.
Interrupted generation requires operator recovery.

## Candidate validation

Under umask `022`, 14 focused TLS/private-file/HTTPS/WSS tests and 5 managed-startup
tests passed in separate invocations. The combined run exposed transient lock contention
in the startup fixture during concurrent process generation; the production lock policy
was not changed. The release build passed with zero warnings. Tests use synthetic keys,
memory-only identity import, ephemeral ports and no real app/Shortcut/audio executor.
The ownership oracle varies synthetic `fstat` metadata; no root access or chown is used.
Pre-producer checks prove mode `0600` before private bytes exist; complete generation
also verifies final modes. File snapshots verify unchanged bytes, certificate hashes,
permissions, owner, links and inodes after secure load or refusal. Permission-only
remediation is rehearsed on a synthetic identity. No physical-device result is claimed.
An external synthetic rehearsal also verified a metadata-preserving `ditto` child copy
inside its unchanged `0700` enclosure, and descriptor-based mode rollback without byte changes.

## Separate production permission remediation — prepared, not executed

Metadata-only inspection on 2026-11-11 found UID 501, regular files, one link and no
ACL entries for all three secrets. `ca.key` is `0600`; `server.key` and `server.p12`
are `0644`; the configuration/TLS directories are `0755`. No private contents were
read and no production permissions were changed.

Before a future permissions-only operation:

1. Obtain explicit authorization for the installation and operation. Reverify current
   LaunchAgent PID/start, executable/source receipt, sandbox, listeners and TLS path.
   A permissions-only change needs no service stop/restart or candidate deployment.
2. Record device/inode, owner, mode, links, type, ACL/xattrs and timestamps. Refuse
   symlinks, unexpected owners/links/ACLs or writable directories; do not use chown,
   ACL deletion or replacement keys to work around a failed precondition.
3. Create a fresh operator-owned `0700` backup enclosure outside live TLS. Copy into
   its separate child: `/usr/bin/ditto --rsrc --extattr --acl <live-tls> <backup>/tls`.
   Never copy onto the enclosure itself; recheck its owner and `0700` mode afterwards.
   Verify the private backup and retain
   the previous binary/resources/profile/LaunchAgent receipt. The `0700` enclosure must
   protect the backup's original `0644` files. Never paste private bytes into reports.
4. Record public CA/server certificate fingerprints and IP mapping privately. Inventory
   current token, complete V2 and approvals using existing protected-state procedures.
   Preserve Open ChatGPT UUID `CE71C698-08EA-4D59-8C91-53790C9EDFF8`, all seven controls,
   IDs/order/titles/parameters, unknown fields and widgets. Revision `e877d78bd16a5d15`
   is superseded; never restore it or a stale V2 snapshot.
5. Open only the reviewed `0644` files with `O_NOFOLLOW | O_NONBLOCK`. Immediately
   validate descriptors against recorded device/inode, UID, regular type, single link
   and ACL state; apply `fchmod(fd, 0600)` and recheck each descriptor and named inode.
   Leave `ca.key` alone if still secure. No recursive chmod, chown, replacement or OpenSSL.
6. Verify unchanged bytes/identity/IP mapping and protected state; only intended mode/ctime
   changes are expected. Verify authenticated HTTPS and WSS with the existing pinned-identity
   health procedure, keeping credentials agent-invisible and executing no control.

Synthetic validation proves that correcting only those modes permits the identical
PKCS#12/CA/certificates/IP stamp to load, leaving public files unchanged. Production
compatibility after remediation remains a future gate. No token/certificate rotation is needed.

## Rollback and stop conditions

The metadata receipt and private TLS backup must exist before future mutation; S2 creates
neither production backup nor remediation. On failure, stop and preserve the running service
and evidence. No restart, rotation, regeneration or retry around a failed precondition.
The previous binary can read owner-only material, so keeping `0600` is the preferred rollback.
If Steering separately authorizes exact metadata rollback, revalidate the same descriptors
and restore only recorded modes of files this operation changed. This reopens the known
exposure and is never automatic. Never restore a whole old configuration or newer V2/approval
state. Any identity-byte mismatch requires a separate recovery decision using the verified
backup. Synthetic permission compatibility is tested; production backup/remediation,
candidate cutover and physical acceptance are not performed by this task.
